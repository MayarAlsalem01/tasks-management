## Architecture

This is a freshly scaffolded App Router project (the "tasks-management" app hasn't been built yet). Source lives in `src/app/`, and the `@/*` import alias maps to `src/*`.

Settings in `next.config.ts` that change how code has to be written:

- **`cacheComponents: true`**: Cache Components mode. Data fetching is dynamic by default. Cache with the `"use cache"` directive (plus `cacheLife` / `cacheTag`), and wrap uncached or runtime data access (`cookies()`, `headers()`, uncached fetches) in `<Suspense>` boundaries. Route segment configs like `export const dynamic` / `revalidate` don't apply in this mode. See `02-guides/migrating-to-cache-components.md` and `01-getting-started/08-caching.md`.
- **`partialPrefetching: true`**: see `02-guides/adopting-partial-prefetching.md`.
- **`reactCompiler: true`** (via `babel-plugin-react-compiler`): memoization is automatic, so manual `useMemo` / `useCallback` / `memo` usually aren't needed.
- **Tailwind CSS v4** loads through a Turbopack rule (`@tailwindcss/turbopack`), not PostCSS. Configuration is CSS-first in `src/app/globals.css` (`@import "tailwindcss"`, `@theme inline`). There's no `tailwind.config.js`. The theme is the light-only **Fractals** design system (called "Specline" in the original design files). shadcn semantic vars (`--primary`, `--border`, …) live in `:root`, and the design tokens live in `@theme`: `gray-*`/`cobalt-*`/`success|warning|danger|info-*` colors, `text-display|title-1|title-2|title-3|body|ui|caption|overline`, `shadow-e1|e2|e3|focus`, and radius `xs 4 / md 6 / lg 8 / xl 12`.
- **UI components** come from **shadcn/ui** (Radix, `components.json`) in `src/components/ui/`, already restyled to the Fractals design system. Add new ones with `npx shadcn@latest add <name>` and adjust them to the tokens. Never overwrite the existing customized files (answer "no" to overwrite prompts). Domain status components (Dev/QA/Spec/Priority pills, PR chip, AC summary) are exported from `@/features/requirements`.

Typed route helpers like `LayoutProps<"/">` / `PageProps<"/...">` are global types that Next generates (see `src/app/layout.tsx`). Use them for layout and page props instead of hand-written prop types.

## Code Architecture & Engineering Standards

Follow these rules on every change. If a rule conflicts with a task, say so and ask; don't silently break it.

### 1. Feature-driven architecture (feature slices)

- Put each business domain in `src/features/<feature-name>/` (kebab-case, e.g. `src/features/task-board/`).
- Use these internal folders, and create one only when it has content:
  - `components/`: the feature's UI
  - `hooks/`: client-side stateful logic
  - `actions/`: raw data access (Drizzle queries), domain services and Server Actions
  - `cache/`: the feature's caching layer. `queries.ts` holds the cached readers (`"use cache"` + `cacheTag` + `cacheLife`), and `revalidate.ts` holds the invalidation helpers (`updateTag`). Pages and loaders read through `cache/queries.ts`, never the raw queries in `actions/`.
  - `types/`: domain types and schemas
  - `utils/`: pure helpers
- Expose each feature only through `src/features/<feature-name>/index.ts`. Code outside the feature imports from `@/features/<feature-name>` and never from its internal folders.
- Inside a feature, use relative imports and never import from the feature's own `index.ts`, since that creates circular imports.
- Put shared code in these places:
  - `src/components/ui/`: base UI primitives
  - `src/hooks/`: generic hooks
  - `src/lib/`: API client, error handling, config and generic utilities
- Features may import shared modules. Shared modules must never import from `src/features/`.
- Cross-feature imports go one way only. Circular dependencies between features are forbidden. If two features need the same thing, move it into shared code or a new feature.
- Keep the server/client boundary out of the barrels:
  - Start every server-only module (DB access, secrets, services) with `import "server-only"`.
  - Don't re-export server-only code and client components from the same barrel if a client component imports that barrel. Split it into separate entry points instead, e.g. `index.ts` plus `server.ts`.
- Keep `src/app/` routes thin. They handle routing, layouts, page shells, `metadata`, `<Suspense>` boundaries, and reading `params`/`searchParams`. Build each page from compositions exported by `features/`, and keep business logic, data transformation and large JSX trees out of `app/`.

### 2. Pragmatic DRY

- When business logic, a data transformation or a state/validation schema is needed in a second place, extract it into a utility, hook or schema right away. Use the owning feature, or `src/lib/` if more than one feature needs it.
- Use one API client, one error-handling path and one mutation pattern from `src/lib/`. Never write a one-off `fetch` wrapper or a new error-shaping helper.
- Don't merge separate domain concepts just because their code looks alike today. Duplicating two lines is fine. Merging two different concepts into one abstraction is not.
- Prefer composition (props, children, small hooks) over inheritance, config-flag-heavy components and early generic abstractions.

### 3. Strict single responsibility

- **Client components** only present UI and handle user interaction:
  - No `fetch` calls.
  - No business calculations.
  - No side effects in the render body.
  - Move state logic into hooks and calculations into `utils/`.
- **Server components** may `await` data, but only by calling the feature's cached readers in `cache/queries.ts`. No inline `fetch`, SQL or data reshaping in JSX files.
- **Hooks** own exactly one state machine, lifecycle or business concern (`useTaskFilters`, not `useTaskManagement`).
- **Utilities** are pure and deterministic. They do one task, take inputs as parameters, and have no hidden side effects or module-level mutable state.
- **Server Actions and Route Handlers** do only three things, in order:
  1. Validate the input.
  2. Check authentication and authorization.
  3. Call a domain service in `api/` and return its result.

  No business logic inline.

### 4. Balanced granularity (the "Goldilocks rule")

- **Avoid monoliths:**
  - Keep components and hooks under about 100–120 lines. Past that, split out sub-components or move stateful logic into a hook.
  - Keep functions under about 25–35 lines. Past that, extract named steps.
- **Avoid over-splitting:**
  - Don't write one-line wrapper functions.
  - Don't write a hook that only wraps one built-in hook without adding logic.
  - Don't make trivial one-line components.
- Keep tightly coupled sub-components next to their parent, in the same file or a sibling file in that feature's `components/`. Don't spread them across nested folders or move them into shared code before a second consumer exists.

### 5. Product naming

- The product is called **Fractals Tasks**. Never hardcode the name "Specline" (that's only the old name in the design files) or any other product name in UI text, metadata or emails.
- Import the name from `@/lib/config`: `APP_NAME` for text and titles, and `APP_MARK` for the one-letter logo mark. A rename then touches one file.
- When you implement a screen from the design project, replace "Specline" and the "S" mark with `APP_NAME` and `APP_MARK`.

### 6. Function documentation

- Add a JSDoc block (`/** … */`) when someone reading only the call site couldn't tell what the code is for. That applies to:
  - exported functions, hooks, Server Actions and domain services
  - session/auth helpers
  - non-trivial components
- Start with one sentence on what it does and why it exists. Then cover only what the types don't show:
  - side effects (DB writes, cookies, redirects, Pusher events, notifications)
  - what it returns or throws on failure
  - the business or security rule it enforces, with its FRS id (e.g. `FR-WKF-001`)
  - any caller requirement (e.g. "must sit inside `<Suspense>`")
- Use `@param` / `@returns` / `@throws` only when they add something beyond the TypeScript types.
- Skip JSDoc on code that is obvious from its name and types, such as simple presentational components and small private helpers. Don't restate the code.
- Inline comments explain *why* (a constraint, a workaround, a non-obvious decision), never *what*.
- When you change behaviour, update its doc comment in the same change.

### 7. Authorization

- Check access in every page, loader and Server Action that reads or changes protected data:
  - `requireUser()`, or `requireAdminPage()` for admin pages
  - `requireAdmin()` / `requireRole()` in actions
  - project access checks in services
- **Never rely on a layout check alone.** Layouts and pages render in parallel, so a layout redirect doesn't stop the page from streaming its data.
- Services scope queries to the caller (e.g. notifications by `user_id`). They never trust ids from the client without checking ownership or access.

### 8. Error handling

- **One path.** `src/lib/errors.ts` is the only error toolkit:
  - `AppError` (a typed `code` plus a message that is safe to show users)
  - `logError(error, context, details?)`
  - `toUserMessage(error)`
  - `GENERIC_ERROR_MESSAGE`

  Don't create other error classes, loggers or message helpers. Libraries' own error types (e.g. Better Auth's `APIError`) are caught and translated at the boundary.
- **Expected failures are values.** Validation errors, wrong credentials, missing permissions, not found and conflicts are expected. Services return them as discriminated-union results or throw `AppError`. Server Actions return a typed state like `{ status: "error", message }` for the UI to render.
- **Errors in Server Actions:** form actions return `ActionState` from `src/lib/action-state.ts`.
  - Validation failures return `validationErrorState(zodError)`.
  - Wrap auth and the service call in `try/catch`, and return `actionErrorState(error, "feature.action")` from the `catch`. It rethrows Next.js control flow (`redirect` / `notFound`), shows an `AppError`'s message (inline when it has a `field`), and logs anything else before returning the generic message.
  - Keep `redirect()` outside the `try`.
- **Server Component reads let unexpected errors propagate** to the nearest `error.tsx`. Never turn a failed read into empty data or "signed out".
- **No silent catches.** Every `catch` recovers in a meaningful way, rethrows, or calls `logError` with a `context` like `"feature.function"`. A secondary side effect that mustn't break the main flow (e.g. updating `last_login_at` after sign-in) is caught and logged, not ignored.
- **Never send raw errors to the client:**
  - Never return `error.message` from an unknown error, or stack traces or SQL details.
  - Messages must not reveal whether an account exists.
- **Boundaries.** `src/app/error.tsx` and `src/app/global-error.tsx` render the shared `ErrorState` (`@/components/ui/error-state`), which logs once and offers `retry` (Next 16 passes `retry`, not `reset`). Add an `error.tsx` to any route group that needs its own fallback.
- **Client components** show errors through the action state or a toast (`sonner`). They never `throw` for expected failures.

### 9. Caching, streaming and loading states

- **Cache every server read with `"use cache"`** in the feature's `cache/queries.ts`:
  - Tag it with the domain tags it depends on (`CacheTag` in `src/lib/cache-tags.ts`, or a per-user tag like `notificationsTag(userId)`).
  - Give it a lifetime from `CacheProfile`.
  - Arguments form the cache key, so pass plain values (ids, flags, filter objects), never request objects.
  - Cached functions can't read `cookies()` / `headers()`. Read the session outside (e.g. `requireUser()`) and pass ids in.
- **Every mutation invalidates what it changed.** After a successful write, the Server Action calls the feature's `cache/revalidate.ts` helper (`updateTag`, Server Actions only), invalidating every tag whose data changed, including other domains (e.g. user changes also refresh `CacheTag.Projects`, since memberships live there). Don't use `refresh()` or `revalidatePath` for data the tags cover.
- **Keep the static shell static.** Page frames, headers, titles, breadcrumbs, buttons and tabs without data render outside `<Suspense>`, so they're prerendered and show instantly on navigation. Only the parts that need the session, `params`/`searchParams` or data go inside `<Suspense>`, as small async components. Never `await` data at the top of a page or layout that also renders static UI.
- **Every `<Suspense>` gets a skeleton** that matches the final layout's size: tables use `TableSkeleton` with the real column template, plus feature skeletons like `UsersSkeleton`, `SidebarSkeleton`, `NotificationsSkeleton`. No empty fallbacks for visible content, and no spinners for page sections.

### 10. Constants instead of string literals

- Don't scatter magic strings. Use the shared constants (`as const` objects with a derived type):
  - routes and query keys: `ROUTES`, `ProjectView`, `SearchParam` and `withQuery()` from `src/lib/routes.ts`
  - cache tags: `CacheTag` / `CacheProfile` from `src/lib/cache-tags.ts`
  - audit codes: `AuditEntity` / `AuditAction` from `src/lib/audit.ts`
  - role labels: `ROLES` / `ROLE_LABELS` from `src/lib/auth/roles.ts`
  - DB constraint names: `UniqueConstraint` from `src/lib/db/errors.ts`
  - the credential provider id: `CREDENTIAL_PROVIDER`
- When a new set of fixed values appears (statuses, event names, Pusher channels, notification types), add a constant object next to its owner and import it. DB enums stay the source of truth for persisted values.

### 11. Validation (Zod)

- Validate every input with a **Zod** schema before using it:
  - form data
  - Server Action arguments, including ids (`idSchema` from `src/lib/validation.ts`) and flags
  - `searchParams` (e.g. `parseUserFilters`)
  - route params and any external payloads
- Schemas live in the feature's `types/`. Shared rules live in `src/lib` (`usernameSchema`, `passwordSchema`). Client forms and Server Actions use the same schema, so the rules never differ.
- Use `safeParse` in actions and return `validationErrorState(error)`. URL parsing drops bad values (`.catch(undefined)`) instead of throwing.

### 12. Client-side data fetching (React Query)

- Server Components load data on the server through the cached readers. That's the default.
- When a Client Component must fetch, poll or optimistically update data after the first render (e.g. live notification counts, drag-and-drop status changes), use **TanStack React Query** (`QueryProvider` in the root layout):
  - Put `useQuery` / `useMutation` in a feature hook.
  - Keep query keys in the feature's `cache/query-keys.ts`.
  - Fetch through a Server Action or route handler.
  - Use `onMutate` for optimistic updates, with rollback on error.
- Never fetch with `useEffect` + `fetch` or keep server data in `useState`.
